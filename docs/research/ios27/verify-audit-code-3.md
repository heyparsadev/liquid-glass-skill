## Finding 16 — **CONFIRMED**

> `.toolbar(.hidden, for: .tabBar)   // hides only within this stack`

- **Established truth:** The finding is correct. `nonisolated func toolbar(_ visibility: Visibility, for bars: ToolbarPlacement...) -> some View` (iOS/iPadOS/Mac Catalyst/tvOS 16.0+, macOS 13.0+, watchOS 9.0+, visionOS 1.0+) carries DocC metadata `deprecatedAt: "27.2"` and `renamed: "toolbarVisibility(_:for:)"` on iOS, iPadOS, Mac Catalyst, macOS, tvOS and watchOS. visionOS has neither key. `deprecated` is false on every platform, so this is a scheduled deprecation. The replacement is `nonisolated func toolbarVisibility(_ visibility: Visibility, for bars: ToolbarPlacement...) -> some View`, available on iOS 18.0+, iPadOS 18.0+, Mac Catalyst 18.0+, macOS 15.0+, tvOS 18.0+, visionOS 2.0+ and watchOS 11.0+, with no deprecation keys. patterns/glass-tab-bar.md:79 should therefore read `.toolbarVisibility(.hidden, for: .tabBar)`, which works with the skill's iOS 26 minimum.
- **Evidence:** https://developer.apple.com/documentation/swiftui/view/toolbar(_:for:)
- **Notes:** Fetched swiftui/view/toolbar(_:for:).json twice and quoted the raw platforms array both times: deprecatedAt "27.2" and renamed on 6 platforms, visionOS entry `{"introducedAt":"1.0","deprecated":false}` only, and no top-level deprecationSummary. toolbarVisibility(_:for:).json gives the declaration and availability exactly as the finding states, and its discussion has the same samples, including `.toolbarVisibility(.hidden, for: .navigationBar, .tabBar)`. The SwiftUI updates page (first 100k chars, covering the September and June 2026 sections) does not mention this deprecation. Repo check: glass-tab-bar.md:79 is `.toolbar(.hidden, for: .tabBar)   // hides only within this stack`.

## Finding 18 — **CONFIRMED**

> Comment: '`.white` and `.primary` are different ShapeStyle types, so neither can be selected with a ternary — branch on the whole button instead.'

- **Established truth:** The comment at 07-ProfileScreen.swift:52-54 is half wrong. Color declares both `static let white: Color` and `static let primary: Color` (iOS 13.0+, iPadOS 13.0+, Mac Catalyst 13.0+, macOS 10.15+, tvOS 13.0+, visionOS 1.0+, watchOS 6.0+). So `.foregroundStyle(cond ? .white : .primary)` can resolve both branches as Color. Written on their own, `.foregroundStyle(.primary)` resolves to `ShapeStyle.primary: HierarchicalShapeStyle` and `.white` resolves to `ShapeStyle.white: Color`, which is probably where the mistake came from, but that does not block the ternary. The tint pair works the same way through `tint(_ tint: Color?)` (iOS 15+), using `static var accentColor: Color { get }` and `static let clear: Color`. Only the ButtonStyle half of the comment is true: GlassButtonStyle and GlassProminentButtonStyle are separate structs (each conforms to PrimitiveButtonStyle, iOS 26.0+), so a ternary cannot pick between them.
- **Evidence:** https://developer.apple.com/documentation/swiftui/color/primary
- **Notes:** Apple docs checked: color/primary, color/white, color/accentcolor, color/clear, shapestyle/primary (HierarchicalShapeStyle, iOS 15+), shapestyle/white (Color), view/tint(_:) (a Color? overload plus a generic S? overload), glassbuttonstyle and glassprominentbuttonstyle. Whether the ternary type-checks is Swift compiler behavior that the docs cannot show, and there is no compiler here. It is backed by the repo's own 06-ChatScreen.swift:150 (`.foregroundStyle(message.fromMe ? .white : .primary)`) and by 1,588 GitHub code-search hits for the exact string `foregroundStyle(isSelected ? .white : .primary)`, including established projects (secondary source). One small difference: inside the ternary, `.primary` becomes Color.primary (a fixed semantic color) rather than the hierarchical `.primary`, which follows the current foreground style. Both look the same here. 08:219 and 09:148 contain only the correct ButtonStyle sentence.

## Finding 20 — **CONFIRMED**

> HydrationStrip, the content of `.tabViewBottomAccessory`, contains a `.buttonStyle(.glassProminent)` '+250 ml' button. patterns/glass-tab-bar.md:62 likewise puts a `.buttonStyle(.glass)` play button inside the accessory.

- **Established truth:** Confirmed as design guidance. The tab-view bottom accessory is part of the system tab-bar chrome. WWDC25-284 says 'UITabBarController displays the accessoryView above the tab bar, matching its appearance.' HIG Tab bars says tab bar items 'rest on a Liquid Glass background' and mentions 'tab bars with an attached accessory, like the MiniPlayer in Music.' That makes the `.buttonStyle(.glassProminent)` button at 09-HealthTodayScreen.swift:594 and the `.buttonStyle(.glass)` button at glass-tab-bar.md:62 glass on glass. Adopting Liquid Glass (Controls section) says to 'avoid overcrowding or layering Liquid Glass elements on top of each other.' WWDC25-219 is more direct: 'always avoid glass on glass… When placing elements on top of Liquid Glass, avoid applying the material to both layers. Instead, use fills, transparency, and vibrancy for the top elements.' The tabViewBottomAccessory(content:) doc says: 'On iPhone… when the tab bar is collapsed, the accessory displays inline.' `enum TabViewBottomAccessoryPlacement` has two cases, `expanded` ('The bar is expanded on top of the bottom tab bar…') and `inline` ('The view is displayed in line with the bottom tab bar.'). The enum is 26.0+ on all seven platforms, but the modifier itself is only iOS, iPadOS and Mac Catalyst 26.0+.
- **Evidence:** https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass
- **Notes:** Every quote above was checked verbatim. Two caveats. (1) 'Apple's samples show no glass-styled buttons' is true but weak evidence: WWDC25-323's MusicPlaybackView body is only `// compact layout` / `// full layout`, and the DocC samples show `ControlsPlaybackView()`, `SliderPlaybackView()` and `HomeStatusView()` without their contents. (2) The skill contradicts itself here. Checklist line 21 allows 'Maximum two glass layers stacked', and references/02-hig-principles.md:65 says a glass card on a glass nav bar is OK. On the other hand, anti-pattern #11 ('Re-glassing system chrome') and layering rule 2 ('Glass cannot sample other glass… lensing effect is lost') support the finding. Apple describes GlassButtonStyle only as 'based on the button's context' and does not say how it renders inside the accessory. Nothing was checked on a device.

## Finding 21 — **CONFIRMED**

> Each of the six MetricChip content cards (icon, title, value, unit, chevron) gets `.glassEffect(.regular.tint(metric.tint.opacity(0.18)), in: .rect(cornerRadius: 20))`.

- **Established truth:** The finding is correct. MetricChip (09-HealthTodayScreen.swift:434-463) is a content-layer data card: icon, chevron, title, value and unit inside a horizontal ScrollView. Each card gets its own tint, `.glassEffect(.regular.tint(metric.tint.opacity(0.18)), in: .rect(cornerRadius: 20))`, in six colors: green, red, indigo, teal, blue and orange. HIG Materials: 'Don't use Liquid Glass in the content layer… Instead, use standard materials for elements in the content layer, such as app backgrounds.' Its only exception is transient controls such as sliders and toggles. The cards also break the skill's own golden rule 1 and checklist line 20 ('No glass on `List` rows, card bodies…'). On tint, WWDC25-323 says 'only use this to convey meaning and not just for visual effect.' WWDC25-219 adds 'Avoid tinting all your elements. When every element is tinted, nothing stands out' and 'If you want to imbue color into your app, do it in the content layer instead.' The cards do sit in GlassEffectContainer(spacing: 10) at 09:241. Each shows `chevron.right`, but no Button, NavigationLink or tap handler wraps them.
- **Evidence:** https://developer.apple.com/design/human-interface-guidelines/materials
- **Notes:** HIG Materials text was quoted from the DocC JSON; the page's change log has 'September 9, 2025: Updated guidance for Liquid Glass'. The WWDC25-323 sentence comes from the Liquid Glass effects chapter ('For especially important views, use a tint modifier. Similar to toolbar buttons, only use this to convey meaning…'). A grep of 09 for Button, NavigationLink and onTapGesture finds nothing around MetricChip, which is used as `MetricChip(metric: m).glassEffectID(...)`.

## Finding 22 — **CONFIRMED**

> `.searchable(…).searchToolbarBehavior(.minimize)` (62-63) is combined with a custom glass quick-action bar pinned via `.safeAreaInset(edge: .bottom)` (69-73).

- **Established truth:** Confirmed as design guidance. Declaration: `nonisolated func searchToolbarBehavior(_ behavior: SearchToolbarBehavior) -> some View`, 26.0+ on iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS. Its doc says: 'On iPhone, the search field in the bottom toolbar can be configured to appear as a button-like control when inactive.' SearchToolbarBehavior.minimize is described as 'prefers rendering a search field as a button-like control.' WWDC25-323 says 'Search in the toolbar places the field at the bottom of the screen.' So in 05-DashboardScreen.swift, where lines 62-63 add .searchable and .minimize inside a NavigationStack, iPhone shows a glass search button in the system bottom toolbar. The `.safeAreaInset(edge: .bottom)` quick-action bar at 69-73 (three `.glass` buttons in a GlassEffectContainer) then sits as a second glass row just above it. Adopting Liquid Glass: 'avoid overcrowding or layering Liquid Glass elements on top of each other.' The idiomatic layout is WWDC25-323's InboxView sample, which puts everything in one system bar: `ToolbarItem(placement: .bottomBar)`, `ToolbarSpacer(.flexible, placement: .bottomBar)`, `DefaultToolbarItem(kind: .search, placement: .bottomBar)`, `ToolbarSpacer(.fixed, placement: .bottomBar)` and another `ToolbarItem(placement: .bottomBar)`. The transcript says 'The Mail app uses this technique to create a leading-aligned filter item and a trailing-aligned group with the search and compose items.' DefaultToolbarItem init(kind:placement:) is 26.0+.
- **Evidence:** https://developer.apple.com/documentation/swiftui/view/searchtoolbarbehavior(_:)
- **Notes:** The declaration and availability match the doc exactly. Apple's own sample on that page has a typo, `.searchToolbarBehavior(.minimized)`, while the actual member is `minimize`. One precision point: the safe-area inset places the custom bar above the toolbar rather than overlapping it, so 'two bottom glass layers' means two stacked bottom glass rows. The 'overcrowding' half of Apple's sentence is the part that applies. Not checked on a device.

## Finding 23 — **PARTIALLY**

> `.confirmationDialog("Sign out of this account?", …)` is attached to the List inside the NavigationStack, not to the Sign Out button (46-55) that sets `showSignOut`.

- **Established truth:** The guidance is right but the stated availability is wrong. 01-SettingsScreen.swift:66 attaches .confirmationDialog to the List chain instead of the Sign Out button at lines 46-55. WWDC25-323 says 'In the new design, dialogs also automatically morph out of the buttons that present them!', and its sample attaches .confirmationDialog to the presenting toolbar Button. The DocC sample attaches it to `Button("Empty Trash")`. Adopting Liquid Glass (Windows and modals): 'Specify the source of an action sheet. Position an action sheet's anchor next to the control it originates from.' A DocC note says: 'In regular size classes in iOS, the system renders confirmation dialogs as a popover…'. The quoted declaration `nonisolated func confirmationDialog<A>(_ titleKey: LocalizedStringKey, isPresented: Binding<Bool>, titleVisibility: Visibility = .automatic, @ContentBuilder actions: () -> A) -> some View where A : View` is word-for-word correct (DocC path …actions:)-87n66). Its availability, however, is iOS 15.0+, iPadOS 15.0+, Mac Catalyst 15.0+, macOS 12.0+, tvOS 15.0+, visionOS 1.0+, watchOS 8.0+. The iOS 16.0 / macOS 13.0 / watchOS 9.0 set the finding gives belongs to a different overload: the new `@export(implementation)` one that takes `_ titleResource: LocalizedStringResource`, at the path with no suffix.
- **Evidence:** https://developer.apple.com/documentation/swiftui/view/confirmationdialog(_:ispresented:titlevisibility:actions:)-87n66
- **Notes:** I fetched all four overloads. No suffix: LocalizedStringResource, iOS 16+. -87n66: LocalizedStringKey, iOS 15+. -55h6a: Text, iOS 15+. -46zbb: StringProtocol, iOS 15+. `@ContentBuilder` is correct for the Xcode 27 SDK: the raw tokens point to `s:7SwiftUI14ContentBuildera` (a typealias), and the June 2026 SwiftUI updates entry calls ContentBuilder 'the unified replacement for type-specific builders'. The claim that the popover would anchor to the whole List is my inference from the DocC note plus how SwiftUI anchors modifiers; I did not test it. Everything else in the finding, including the line references, checks out.
