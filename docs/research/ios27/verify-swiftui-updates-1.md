# verify:swiftui-updates#1

_Phase: Verify — independent re-check of findings from [swiftui-updates](swiftui-updates.md)_

## Finding 0 — **CONFIRMED**

> Toolbar integration section (iOS 26) has no API to minimize the navigation bar on scroll; only tabBarMinimizeBehavior is taught.

- **Established truth:** The skill does not teach navigation-bar minimization anywhere. 01-api-reference.md §8 'Toolbar integration' (line 298) and the rest of the skill teach only `.tabBarMinimizeBehavior(_:)` for bar minimization; `.searchToolbarBehavior(.minimize)` minimizes the search field, not the bar. iOS 27 adds `nonisolated func toolbarMinimizationBehavior(_ behavior: ToolbarMinimizationBehavior, for bars: ToolbarPlacement...) -> some View`, introduced in iOS/iPadOS/Mac Catalyst/macOS/tvOS/visionOS/watchOS 27.0, not beta, not deprecated. `struct ToolbarMinimizationBehavior` has exactly four members: `static var automatic`, `static let never`, `static let onScrollDown`, `static let onScrollUp`. The finding's discussion quote is verbatim. WWDC26 session 269 'What's new in SwiftUI' (code at 7:37 and the transcript) uses `.toolbarMinimizeBehavior(.onScrollDown, for: .navigationBar)`, a name that is not in the shipping docs. The iOS & iPadOS 27 Release Notes (SwiftUI, New Features) say verbatim: 'You can use toolbarMinimizationBehavior to control bar minimization behavior. This modifier replaces toolbarMinimizeBehavior. (177954148)'. Teach only `toolbarMinimizationBehavior`, gated with `#available(iOS 27, *)` because the skill targets iOS 26+.
- **Evidence:** https://developer.apple.com/tutorials/data/documentation/swiftui/view/toolbarminimizationbehavior(_:for:).json
- **Notes:** Declaration, all 7 platform versions (27.0, beta:false, deprecated:false) and the discussion text match the Apple JSON exactly. The discussion also says verbatim: 'By default, the safe area adjusts as the navigation bar minimizes. Use toolbarMinimizationSafeAreaAdjustment(_:for:) to customize this.' The `automatic` abstract says verbatim: 'The system determines the minimize behavior. By default, navigation bars on iOS will minimize when the view has a searchable using the toolbarPrincipal placement.' Both swiftui/view/toolbarminimizebehavior(_:for:).json and swiftui/toolbarminimizebehavior.json return HTTP 404. The updates page (June 2026 > Toolbars) lists only toolbarMinimizationBehavior(_:for:). The WWDC code spelling was checked twice at https://developer.apple.com/videos/play/wwdc2026/269/ and the release note at https://developer.apple.com/tutorials/data/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes.json (offset 60000–100000+). That release-notes page is the cumulative beta notes (entries reference betas 1–5). It also has the UIKit counterpart (177953926): UINavigationItem.navigationBarMinimization replaces barMinimizeBehavior and barMinimizationSafeAreaAdjustment. In the skill, tabBarMinimizeBehavior appears at 01-api-reference.md lines 372-376 and 566, and in patterns/glass-tab-bar.md and examples/09.

## Finding 1 — **CONFIRMED**

> Skill has no control over when a minimized bar restores.

- **Established truth:** The skill has nothing that controls minimized-bar restoration. iOS 27 adds `nonisolated func toolbarMinimizationRestoration(_ restoration: ToolbarMinimizationRestoration, for bars: ToolbarPlacement...) -> some View`, introduced in iOS/iPadOS/Mac Catalyst/macOS/tvOS/visionOS/watchOS 27.0, not beta or deprecated. `struct ToolbarMinimizationRestoration` has exactly two members: `static let atScrollEdge` ('The toolbar restores only when the scroll view's content reaches the scroll edge.') and `static let automatic` ('The system determines the restoration behavior.'). The docs say verbatim: 'By default, the bar restores when the user reverses scroll direction. Use atScrollEdge to restrict restoration to when the scroll view's content reaches the scroll edge – appropriate for screens where the bar is mostly chrome that doesn't need to follow the user.' and 'Currently, only navigationBar supports customizing the restoration behavior, and only when used in combination with onScrollDown.' The API only makes sense together with `.toolbarMinimizationBehavior(.onScrollDown, for: .navigationBar)`.
- **Evidence:** https://developer.apple.com/tutorials/data/documentation/swiftui/view/toolbarminimizationrestoration(_:for:).json
- **Notes:** The declaration, availability (all 27.0) and both quoted passages match exactly. The members were confirmed at https://developer.apple.com/tutorials/data/documentation/swiftui/toolbarminimizationrestoration.json under the topic section 'Getting restoration options'; the type conforms to Equatable, Hashable and Sendable. The doc's code sample chains `.toolbarMinimizationBehavior(.onScrollDown, for: .navigationBar)` with `.toolbarMinimizationRestoration(.atScrollEdge, for: .navigationBar)`. This modifier has no bullet of its own on the SwiftUI updates page and is not mentioned in WWDC26 session 269, but its doc page is non-beta and listed under 'Minimizing a toolbar'. A grep of the whole skill for 'restor' found nothing.

## Finding 2 — **PARTIALLY**

> Full-bleed media examples have no way to stop content reflowing when the nav bar minimizes.

- **Established truth:** The API facts are exactly right, but the claim does not fit the file it is attached to. iOS 27 adds `nonisolated func toolbarMinimizationSafeAreaAdjustment(_ adjustment: ToolbarMinimizationSafeAreaAdjustment, for bars: ToolbarPlacement...) -> some View`, introduced in all seven platforms at 27.0, not beta. `struct ToolbarMinimizationSafeAreaAdjustment` has exactly `static let automatic` ('The system determines the safe area adjustment.'), `static let disabled` ('The safe area remains unchanged as bars minimize.') and `static let enabled` ('The safe area adjusts interactively as bars minimize.'). The discussion quote is verbatim. However, examples/04-PhotoDetailScreen.swift has no NavigationStack and no navigation bar: it is a ZStack whose photo uses `.ignoresSafeArea()`, with a custom glass close button and a custom bottom glass toolbar. Nothing in it minimizes or reflows, so the API cannot be applied there as written. Better targets are screens with a NavigationStack over full-bleed content: patterns/glass-navigation-bar.md line 59 (full-bleed image with `.toolbarBackground(.hidden, for: .navigationBar)`) and examples/07-ProfileScreen.swift (NavigationStack + ScrollView `.ignoresSafeArea(edges: .top)` hero). Even there it only matters after opting in with `.toolbarMinimizationBehavior(.onScrollDown, for: .navigationBar)`.
- **Evidence:** https://developer.apple.com/tutorials/data/documentation/swiftui/view/toolbarminimizationsafeareaadjustment(_:for:).json
- **Notes:** The discussion says verbatim: 'By default, the safe area adjusts as bars minimize, allowing content to reflow into the space vacated by the bar. Use this modifier to disable that adjustment when content should remain in place – for example, when displaying full-bleed media beneath a minimizing bar.' and 'Currently, only ... navigationBar supports customizing the safe area adjustment.' The doc sample uses `.toolbarMinimizationSafeAreaAdjustment(.disabled, for: .navigationBar)` after `.toolbarMinimizationBehavior(.onScrollDown, for: .navigationBar)`. The members were confirmed at https://developer.apple.com/tutorials/data/documentation/swiftui/toolbarminimizationsafeareaadjustment.json (topic section 'Minimization adjustment options'). I read examples/04-PhotoDetailScreen.swift in full and it contains no NavigationStack or .toolbar. Its photo already ignores the safe area, so a safe-area change would not move it anyway. The UIKit equivalent, barMinimizationSafeAreaAdjustment, was folded into UINavigationItem.navigationBarMinimization (iOS 27 release note 177953926).

## Finding 3 — **CONFIRMED**

> Skill only teaches ToolbarSpacer/ToolbarItemGroup for arranging glass toolbar items and gives no way to control which items survive when space shrinks.

- **Established truth:** The skill teaches ToolbarItemGroup/ToolbarSpacer (01-api-reference.md §`ToolbarSpacer` at line 317), badges and sharedBackgroundVisibility. It has nothing for overflow priority. iOS 27 adds `@MainActor @preconcurrency func visibilityPriority(_ priority: ToolbarItemVisibilityPriority) -> some ToolbarContent`, available in iOS 27.0, iPadOS 27.0, Mac Catalyst 27.0, macOS 26.1, tvOS 27.0, visionOS 27.0 and watchOS 27.0 per Apple's JSON (the macOS 26.1 really is in the data). `struct ToolbarItemVisibilityPriority` has members `static let automatic`, `static let low`, `static let high`, `init(lowerThan:)` and `init(higherThan:)`. The quote 'When toolbar space is limited, items with a lower priority move into the overflow menu before items with a higher priority. The default is automatic.' is verbatim. The WWDC26 session 269 sample at 6:15 is `ToolbarItemGroup { UndoButton(); RedoButton() }.visibilityPriority(.high)`.
- **Evidence:** https://developer.apple.com/tutorials/data/documentation/swiftui/toolbarcontent/visibilitypriority(_:).json
- **Notes:** The struct page (https://developer.apple.com/tutorials/data/documentation/swiftui/toolbaritemvisibilitypriority.json) has the same platform list with macOS 26.1. Its topic sections are 'Getting system priorities' and 'Creating custom priorities', and it conforms to Comparable, Equatable, Hashable and Sendable. One inconsistency: the raw JSON for the `.high` member lists only iOS/iPadOS/Mac Catalyst 27.0 and macOS 26.1, with no tvOS, visionOS or watchOS, so treat non-iOS/macOS use with care. Apple's own doc example applies it to a `ToolbarItem { PrimaryControl() }`. The updates page (June 2026 > Toolbars) says verbatim: 'Use the visibilityPriority(_:) modifier to prioritize important toolbar actions so SwiftUI keeps them visible as space shrinks, moving lower-priority items to the overflow menu first.' A related point the finding does not make: the HIG 'Designing for iPhone Duo' page says 'Group related toolbar items instead of spacing them manually... avoid adding fixed spacing yourself.' That cuts against the skill's `ToolbarSpacer(.fixed, ...)` teaching (line 325; examples/09 line 112), though the guidance is scoped to iPhone Duo.

## Finding 4 — **CONFIRMED**

> Skill has no way to send secondary toolbar actions to the system overflow (ellipsis) menu.

- **Established truth:** The skill has no way to put actions into the system overflow menu. iOS 27 adds `nonisolated struct ToolbarOverflowMenu<Content> where Content : View`, which conforms to CustomizableToolbarContent and ToolbarContent. Its initializer is `nonisolated init(@ContentBuilder content: () -> Content)`; the finding's `init(content: () -> Content)` is only the abbreviated topic-list form. The view modifier is `nonisolated func toolbarOverflowMenu<C>(@ContentBuilder content: () -> C) -> some View where C : View`. `@ContentBuilder` is real: SwiftUI documents `typealias ContentBuilder = ViewBuilder`. Availability is iOS 27.0, iPadOS 27.0, Mac Catalyst 27.0 and visionOS 27.0; macOS, tvOS and watchOS are not listed. The overview quote is verbatim. The HIG text is verbatim from 'Designing for iPhone Duo' (new page, September 9, 2026): 'Use the system overflow menu. If your app has its own overflow menu, move those actions into the system menu so people find everything in one place. Reserve the ellipsis symbol for overflow, and give other menus a distinct symbol. For developer guidance, see ToolbarOverflowMenu (SwiftUI) and additionalOverflowItems (UIKit).'
- **Evidence:** https://developer.apple.com/tutorials/data/documentation/swiftui/toolbaroverflowmenu.json
- **Notes:** Modifier: https://developer.apple.com/tutorials/data/documentation/swiftui/view/toolbaroverflowmenu(content:).json (the declaration tokens show the attribute ContentBuilder). Init: .../swiftui/toolbaroverflowmenu/init(content:).json. HIG: https://developer.apple.com/tutorials/data/design/human-interface-guidelines/designing-for-iphone-duo.json, section 'Vertical controls'. The updates page (June 2026 > Toolbars) says verbatim: 'Send secondary toolbar actions, like archive or delete, directly to the overflow menu by wrapping them in a ToolbarOverflowMenu, keeping your primary toolbar focused on key actions.' WWDC26 session 269 at 6:15 shows `ToolbarOverflowMenu { ChoosePhotoButton(); ExportAsImageButton(); ClearAllStickersButton() }`. Related point the finding does not make: the skill uses the `ellipsis` symbol for a custom expand toggle in examples/04-PhotoDetailScreen.swift:56 and patterns/glass-floating-toolbar.md:29. That conflicts with the iPhone Duo HIG line 'Reserve the ellipsis symbol for overflow'. Those are custom floating glass toolbars, not navigation-bar toolbars, so ToolbarOverflowMenu would not drop in there directly.

## Finding 5 — **CONFIRMED**

> Pattern places the primary/share action with .topBarTrailing, which can move into overflow when space is tight.

- **Established truth:** The API is exactly as stated: `static let topBarPinnedTrailing: ToolbarItemPlacement`, available in iOS 27.0, iPadOS 27.0, Mac Catalyst 27.0 and visionOS 27.0, not beta. Docs, verbatim: 'A placement that pins the item to the trailing edge of the toolbar.' / 'Pinned items only move to the overflow menu when search is active and there isn't enough room.' / 'On iOS and visionOS, the top bar is the navigation bar.' The line anchor is imprecise. Line 22 of patterns/glass-navigation-bar.md is the 'Filter' button (with 'Profile' at line 25), not a primary or share action. The file's primary action is the `.glassProminent` 'Save' button at lines 37-38, also `.topBarTrailing`. The file has no share action. The `.topBarTrailing` Share buttons that best match WWDC's pinned-Share example are in examples/07-ProfileScreen.swift:45-46 and examples/09-HealthTodayScreen.swift:113-114. Those are the natural candidates for `.topBarPinnedTrailing`, under `#available(iOS 27, *)`.
- **Evidence:** https://developer.apple.com/tutorials/data/documentation/swiftui/toolbaritemplacement/topbarpinnedtrailing.json
- **Notes:** The topBarTrailing doc page (iOS 14.0+, `@backDeployed(before: iOS 17.0, tvOS 17.0)`) says nothing about overflow. That non-pinned trailing items can overflow comes from other sources. topBarPinnedTrailing's own discussion implies it. The updates page (June 2026 > Toolbars) says verbatim: 'Anchor a toolbar item to the trailing edge of the top bar using the topBarPinnedTrailing placement so it stays in place even as other items shift or move to the overflow menu.' The WWDC26 session 269 transcript says 'Important actions like Undo, Redo, and Share are hidden in the overflow menu!' and 'I can use the new topBarPinnedTrailing placement to make the Share button always visible in the trailing position.' Its code is `ToolbarItem(placement: .topBarPinnedTrailing) { ShareButton() }` (https://developer.apple.com/videos/play/wwdc2026/269/). I graded this confirmed because the API, the availability and the 'can overflow' premise all hold; only the line and action described in the claim need the correction above.
