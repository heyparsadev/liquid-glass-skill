## Finding 12 — **CONFIRMED**

> 'Scroll extension' snippet: `ScrollView(.horizontal) { … }.scrollExtensionMode(.underSidebar)`.

- **Established truth:** The skill is wrong at references/01-api-reference.md:519. SwiftUI has no `scrollExtensionMode(_:)` modifier, no `ScrollExtensionMode` type and no `.underSidebar` value. Apple's own sample ('Landmarks: Extending horizontal scrolling under a sidebar or inspector') uses no modifier for this. Make the horizontal ScrollView touch the leading and trailing edges of its container, and the system handles the rest: 'When a scroll view touches the sidebar or inspector, the system automatically adjusts it to scroll under the sidebar or inspector and then off the edge of the screen.' The sample adds a leading `Spacer().frame(width:)` inside the `LazyHStack` so the content lines up with the title padding. For background imagery that is not scrolling, use `@MainActor @preconcurrency func backgroundExtensionEffect() -> some View`, available from 26.0 on iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS; there is also `backgroundExtensionEffect(isEnabled:)`. Scroll-edge treatment is a separate API: `nonisolated func scrollEdgeEffectStyle(_ style: ScrollEdgeEffectStyle?, for edges: Edge.Set) -> some View` and `nonisolated func scrollEdgeEffectHidden(_ hidden: Bool = true, for edges: Edge.Set = .all) -> some View`, both available from 26.0 on iOS, iPadOS, Mac Catalyst, macOS, tvOS and watchOS (not visionOS).
- **Evidence:** https://developer.apple.com/documentation/swiftui/landmarks-extending-horizontal-scrolling-under-a-sidebar-or-inspector
- **Notes:** source_type apple-doc. Evidence that the API does not exist: (1) DocC JSON .../swiftui/view/scrollextensionmode(_:).json returns HTTP 404. (2) DocC JSON .../swiftui/scrollextensionmode.json returns HTTP 404. (3) The Scroll views topic collection (.../swiftui/scroll-views.json) has 12 topic sections and none of them lists scrollExtension, extensionMode or underSidebar. Its 'Configuring scroll edge effects' section lists only scrollEdgeEffectStyle(_:for:), scrollEdgeEffectHidden(_:for:), ScrollEdgeEffectStyle and safeAreaBar(edge:alignment:spacing:content:). (4) The SwiftUI updates page (updates/swiftui.json, sections September 2026 / June 2026 / June 2025) has no such API. (5) A web search, including site:developer.apple.com, found no page using either name. The backgroundExtensionEffect() declaration, availability and discussion come from .../swiftui/view/backgroundextensioneffect().json. Its discussion reads: 'apply this to a view in the detail column of a navigation split view so it can extend under the sidebar or inspector region'. The finding's correction is right but incomplete. For the horizontal ScrollView case this snippet was meant to show, Apple's documented approach is layout only: no modifier, just let the scroll view touch the edges. Use that, not backgroundExtensionEffect(), when replacing the snippet. No compiler was used; the conclusion rests on the docs.

## Finding 15 — **CONFIRMED**

> `.sharedBackgroundVisibility(.hidden)` is applied to the `Button` inside `ToolbarItem { … }`.

- **Established truth:** `sharedBackgroundVisibility(_:)` is an instance method on the `ToolbarContent` protocol only: `nonisolated func sharedBackgroundVisibility(_ visibility: Visibility) -> some ToolbarContent`. It is available from 26.0 on iOS, iPadOS, Mac Catalyst and macOS, and not on tvOS, visionOS or watchOS. It must be applied to the toolbar item, not to the view inside it: `ToolbarItem { ProfileButton() }.sharedBackgroundVisibility(.hidden)`. The skill applies it to the `Button` inside the item (references/01-api-reference.md:349). That `Button` is a View with no such member, so the snippet should fail to type-check. Apple's discussion: 'Hiding the effect will cause the item to be placed in its own grouping.'
- **Evidence:** https://developer.apple.com/documentation/swiftui/toolbarcontent/sharedbackgroundvisibility(_:)
- **Notes:** source_type apple-doc and apple-video. The declaration and the platform list (iOS, iPadOS, Mac Catalyst and macOS, all 26.0, none beta or deprecated) were read verbatim from .../swiftui/toolbarcontent/sharedbackgroundvisibility(_:).json. Its DocC example applies the modifier after the `ToolbarItem { BuildStatus() }` closure. The WWDC25 session 323 code sample 'Hide shared glass background' shows `ToolbarItem { ProfileButton() }.sharedBackgroundVisibility(.hidden)`. Evidence that there is no View version: .../swiftui/view/sharedbackgroundvisibility(_:).json returns 404. The Toolbars topic page has no View entry with this name. ToolbarContent's Conforming Types are DefaultToolbarItem, EmptyView, ForEach, Group, ToolbarItem, ToolbarItemGroup, ToolbarOverflowMenu, ToolbarSpacer, ToolbarTitleMenu and TupleContent; neither View nor Button is among them. The Xcode 27 ContentBuilder change (a typealias for ViewBuilder) does not affect this, because member lookup on Button still fails. The compile failure is inferred from the declarations; no compiler was run. The skill's description of what the modifier does ('Detach an item from the shared toolbar glass slab') is consistent with Apple's docs; only where it is attached is wrong.

## Finding 16 — **CONFIRMED**

> `@Environment(\.tabViewBottomAccessoryPlacement)` values: `// .expanded | .collapsed`.

- **Established truth:** `enum TabViewBottomAccessoryPlacement` has exactly two cases. `expanded`: 'The bar is expanded on top of the bottom tab bar, if there is a bottom tab bar, or at the bottom of the tab's content view.' `inline`: 'The view is displayed in line with the bottom tab bar.' There is no `.collapsed`, so the skill's comment `// .expanded | .collapsed` (references/01-api-reference.md:396) should read `.expanded | .inline`. The environment value is optional: `var tabViewBottomAccessoryPlacement: TabViewBottomAccessoryPlacement? { get }`, and 'A nil value corresponds to an undefined placement.' The enum and the environment value are both available from 26.0 on iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS. Neither is beta or deprecated, and no new case had been added as of the iOS 27 docs.
- **Evidence:** https://developer.apple.com/documentation/swiftui/tabviewbottomaccessoryplacement
- **Notes:** source_type apple-doc and apple-video. The cases and abstracts were read verbatim from .../swiftui/tabviewbottomaccessoryplacement.json, whose topics contain only 'Enumeration Cases: expanded, inline'. Its example switches on `case .inline:` and `case .expanded:`. The optional type and the nil note come from .../swiftui/environmentvalues/tabviewbottomaccessoryplacement.json. The WWDC25 session 323 code sample 'Tab bar accessory' uses `if placement == .inline { // compact layout } else { // full layout }`. The transcript wording 'when it collapses into the tab bar area' is probably where the skill's '.collapsed' came from, but no such case exists. Other places in the skill compare against `.expanded` (patterns/glass-tab-bar.md, examples/09-HealthTodayScreen.swift:565), which is valid. The finding's availability list matches the docs exactly.

## Finding 17 — **CONFIRMED**

> `ToolbarItem(placement: .bottomBar) { DefaultToolbarItem(kind: .search, placement: .bottomBar) }`.

- **Established truth:** `DefaultToolbarItem` is declared `nonisolated struct DefaultToolbarItem` and conforms only to `ToolbarContent`, not to `View`. `ToolbarItem` is declared `nonisolated struct ToolbarItem<ID, Content> where Content : View`, with initializer `nonisolated init(placement: ToolbarItemPlacement = .automatic, @ContentBuilder content: () -> Content)`, which is 'Available when … Content conforms to View'. So `ToolbarItem(placement: .bottomBar) { DefaultToolbarItem(kind: .search, placement: .bottomBar) }` (references/01-api-reference.md:422) cannot type-check. Place the item directly in the toolbar builder: `.toolbar { DefaultToolbarItem(kind: .search, placement: .bottomBar) }`. The exact initializer is `nonisolated init(kind: ToolbarDefaultItemKind, placement: ToolbarItemPlacement = .automatic)`, available from 26.0 on iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS.
- **Evidence:** https://developer.apple.com/documentation/swiftui/defaulttoolbaritem/init(kind:placement:)
- **Notes:** source_type apple-doc and apple-video. Sources: .../swiftui/defaulttoolbaritem.json (Conforms To: ToolbarContent only; 26.0 on all seven platforms), .../swiftui/toolbaritem.json, .../swiftui/toolbaritem/init(placement:content:).json and .../swiftui/defaulttoolbaritem/init(kind:placement:).json. The initializer's DocC example puts `DefaultToolbarItem(kind: .search, placement: .bottomBar)` directly inside `.toolbar { }` as a sibling of ToolbarItems and ToolbarSpacer. A second example puts it in a NavigationSplitView column to choose which column shows search in compact layouts. The WWDC25 session 323 sample 'Toolbar items with flexible spacing' does the same. Apple's discussion adds: 'Combinations of kind and placement may be valid on some platforms, but not on others.' Minor imprecision in the finding: its declaration leaves out `nonisolated` on the initializer and the `= .automatic` default for placement. The compile failure is inferred from the generic constraints; no compiler was run. Xcode 27's ContentBuilder (a typealias for ViewBuilder) does not lift ToolbarItem's `Content : View` constraint.

## Finding 18 — **CONFIRMED**

> Same nesting: `ToolbarItem(placement: .bottomBar) { DefaultToolbarItem(kind: .search, placement: .bottomBar) }`.

- **Established truth:** patterns/glass-search-field.md:60 has the same error as finding 17. Wrapping `DefaultToolbarItem(kind: .search, placement: .bottomBar)` inside `ToolbarItem(placement: .bottomBar) { … }` is invalid because `DefaultToolbarItem` is `ToolbarContent`, not a `View`, and `ToolbarItem` requires `Content : View`. Write it as `.toolbar { DefaultToolbarItem(kind: .search, placement: .bottomBar) }` alongside `.searchable(...)`. The initializer is `nonisolated init(kind: ToolbarDefaultItemKind, placement: ToolbarItemPlacement = .automatic)`, available from 26.0 on iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS.
- **Evidence:** https://developer.apple.com/documentation/swiftui/defaulttoolbaritem/init(kind:placement:)
- **Notes:** source_type apple-doc and apple-video. The evidence is the same as for finding 17: DefaultToolbarItem conforms only to ToolbarContent, ToolbarItem is declared `where Content : View`, and both the initializer's DocC examples and the WWDC25 session 323 'Toolbar items with flexible spacing' sample put DefaultToolbarItem directly in the `.toolbar` builder. The initializer's discussion also says a valid DefaultToolbarItem 'will implicitly replace the default-placed instance', which is how a search item gets moved to another placement. I did not check the prose that follows this snippet in the skill ('pins the search field above the tab bar').

## Finding 19 — **CONFIRMED**

> `.controlSize(.extraLarge)  // new in iOS 26 — for floating CTAs` (also used at line 283).

- **Established truth:** `ControlSize.extraLarge` (`case extraLarge`) is not an iOS 26 API. It is available from iOS 17.0, iPadOS 17.0, Mac Catalyst 17.0, macOS 14.0, tvOS 17.0, visionOS 1.0 and watchOS 10.0, and is neither beta nor deprecated. The current DocC abstract reads verbatim: 'A control version that is substantially sized. The largest control size. Resolves to ControlSize.large on platforms other than visionOS.' The comment 'new in iOS 26' at references/01-api-reference.md:268 is therefore wrong as an availability statement. The usage itself compiles back to iOS 17 and needs no `#available(iOS 26, *)` check. One caveat: WWDC25 session 323 says 'And for your most important, prominent actions there is now support for extra large sized buttons', and AppKit's `NSControl.ControlSize.extraLarge` is new in macOS 26.0. So actual extra-large rendering arrived with the 26 design, at least on macOS, and the 'Resolves to large' sentence in the SwiftUI docs may be out of date.
- **Evidence:** https://developer.apple.com/documentation/swiftui/controlsize/extralarge
- **Notes:** source_type apple-doc, apple-video and apple-other. Availability and abstract were read verbatim from .../swiftui/controlsize/extralarge.json; .../swiftui/controlsize.json repeats the same abstract. The caveat rests on three sources. (1) WWDC25 session 323 transcript, 'Controls' chapter: '...the existing controlSize modifier can be applied to a single control or across an entire set of controls. And for your most important, prominent actions there is now support for extra large sized buttons.' The session does not tie this to a platform. (2) .../appkit/nscontrol/controlsize-swift.enum/extralarge.json shows macOS 26.0. (3) An Apple Frameworks Engineer wrote in Developer Forums thread 740326 (Oct 2023) that SwiftUI 'map[s] .extraLarge to .large where necessary on macOS'. UIKit's UIButton.Configuration.Size still lists only mini, small, medium and large. I found no primary source that says how .extraLarge renders on iOS 26 or 27, so do not rewrite the skill to claim it looks the same as .large on iPhone. A safe replacement comment: 'available since iOS 17; the 26 design added extra-large button support (WWDC25)'. The fix covers the comment at line 268 only. The `.controlSize(.extraLarge)` calls at line 283, examples/03-OnboardingFlow.swift:75, examples/08-LoginScreen.swift:367 and references/03-design-tokens.md:40 and 154 are valid code, though the pixel values in the design-tokens file were not verified.
