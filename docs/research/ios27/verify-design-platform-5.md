## Finding 27 — **CONFIRMED**

> A non-interactive Text tag chip gets .glassEffect() inside every card of a scrolling LazyVStack

- **Established truth:** patterns/glass-card-stack.md line 39 really does apply .glassEffect() to a decorative, non-interactive Text(item.tag) chip. The chip is overlaid on every card's cover image inside ScrollView > LazyVStack, and the 'Multiple chips on one cover' variation adds more glass to each card. This goes against Apple's HIG Materials guidance, which has not changed for iOS 27. The last Materials change-log entry is September 9, 2025, and HIG 'What's new' lists no Materials change in June or September 2026. HIG Materials (verbatim): "Don't use Liquid Glass in the content layer. Liquid Glass works best when it provides a clear distinction between interactive elements and content, and including it in the content layer can result in unnecessary complexity and a confusing visual hierarchy. Instead, use standard materials for elements in the content layer, such as app backgrounds. An exception to this is for controls in the content layer with a transient interactive element like sliders and toggles; ..." and "Use Liquid Glass effects sparingly. ... Limit these effects to the most important functional elements in your app." Apple's 'Applying Liquid Glass to custom views' article adds (verbatim): "Creating too many Liquid Glass effect containers and applying too many effects to views outside of containers can degrade performance. Limit the use of Liquid Glass effects onscreen at the same time." The pattern also contradicts the skill's own rules. 06-performance.md line 120 says "Glass cells in a List or LazyVStack are usually wrong (content layer, not chrome)", line 185 says "No glass on list cells or long scroll content", and the layer table in 02-hig-principles.md marks cards as content with no glass. Fix: give content-layer chips a standard material (for example .background(.ultraThinMaterial, in: .capsule)) or a solid or tinted fill, and keep Liquid Glass for navigation-layer and functional controls.
- **Evidence:** https://developer.apple.com/design/human-interface-guidelines/materials
- **Notes:** Primary sources: (1) HIG Materials JSON, apple-other (HIG). Quotes checked word for word. Change log: Sept 9, 2025 'Updated guidance for Liquid Glass'; June 9, 2025 'Added guidance for Liquid Glass'. (2) https://developer.apple.com/design/whats-new/, apple-other. The June 8, 2026 and Sept 2026 entries do not touch Materials. (3) swiftui/applying-liquid-glass-to-custom-views.json, apple-doc. Performance quotes checked word for word. (4) Repo files read to confirm the pattern and the self-contradiction. Line 39 is the .glassEffect() on the tag Text. Related observation, which is my interpretation and not an Apple statement: the 'Action button overlaid on cover' variation puts a .glassProminent button on every card. Persistent buttons in the content layer are not covered by the HIG exception, which names only transient interactive elements like sliders and toggles, so that variation is also worth reviewing.

## Finding 30 — **CONFIRMED**

> "Respect platform idioms: floating buttons on iOS, sidebars on iPad/Mac"

- **Established truth:** The skill's 'floating buttons on iOS, sidebars on iPad/Mac' is still a valid default, but it misses these 27-release changes, all verified. (1) WWDC26 102, Platforms State of the Union: "Sidebars expand to the edges on Mac and iPad, providing clearer structure while still refracting content from your app and the wallpaper. And icons in the sidebar regain their color using your app's accent color ... List and Label APIs provide these updates automatically and support customizing the tint per item." (2) HIG Sidebars change log, June 8, 2026: "Updated guidance for sidebar icon colors, and clarified guidance for the adaptable sidebar style." Guidance: "By default, sidebar icons use your app's accent color." Fixed colors are acceptable "if you use them sparingly". (3) UIKit only. WWDC26 278, 'Modernize your UIKit app': "New in iOS 27, iPhone apps can also opt into sidebars by setting the tab bar controller's sidebar.preferredPlacement to .sidebar." The API is var preferredPlacement: UITabBarController.Sidebar.Placement (iOS, iPadOS, Mac Catalyst and visionOS 27.0). Enum cases are automatic, sidebar and tabBar. On iPhone this is an app choice with no UI toggle, and the system shows the sidebar only when there is enough space, for example a regular horizontal size class; check sidebar.isAvailable. No SwiftUI equivalent was found: the SwiftUI updates for June and September 2026 have none, and the .sidebarAdaptable docs still say "iOS displays a bottom tab bar." (4) WWDC26 269, 'What's new in SwiftUI': iPad apps "automatically take on a distinct appearance when inactive, with the icons and text dimming". Custom views use @Environment(\.appearsActive). (5) iOS & iPadOS 27 release notes: "The menu bar on iPadOS 27.0 and macOS 27.0, as well as context menus on macOS 27.0, present a reduced set of menu item images. By default, SwiftUI now hides all menu item symbol images in most contexts, while non-symbol images remain visible." Use .labelStyle(.titleAndIcon) on a menu item's Label to always show its icon. The system still shows default images for Settings, Share and Print. UIKit uses UIMenuElement.preferredImageVisibility. HIG Menus was updated June 8, 2026 for menu item icons.
- **Evidence:** https://developer.apple.com/videos/play/wwdc2026/102/
- **Notes:** All five parts of the finding's correct_info were checked against primary sources. WWDC26 102, 269, 278 transcripts (apple-video). HIG sidebars.json and menus.json plus design/whats-new (apple-other). uikit/uitabbarcontroller/sidebar-swift.class, preferredplacement.json and placement.json, which give iOS 27.0 availability and the cases (apple-doc). ios-ipados-27-release-notes.json, SwiftUI and UIKit New Features (apple-other). swiftui/tabviewstyle/sidebaradaptable.json and updates/swiftui.json (apple-doc). ## Finding 31 — **PARTIALLY**

> Concentric corner trick: .rect(cornerRadius: .containerConcentric)

- **Established truth:** Every fact in the finding is correct, but it misses the main problem with line 152: the skill's token .rect(cornerRadius: .containerConcentric) is not valid SwiftUI on any SDK. The declaration is static func rect(cornerRadius: CGFloat, style: RoundedCornerStyle = .continuous). SwiftUI has no symbol named containerConcentric: none of Shape's 13 rect overloads takes one, and Edge.Corner.Style has only static var concentric, static func concentric(minimum:) and static func fixed(_:). The correct SwiftUI form, iOS 26.0+ on all platforms, is .rect(corners: .concentric, isUniform: Bool = false), or ConcentricRectangle(...) with .concentric(minimum:) for a guaranteed minimum radius. This resolves against a container shape: system-provided, or one set with .containerShape(_:). An Apple DTS engineer confirmed on the forums that the shipping spelling is .rect(corners: .concentric), not .rect(corner: .containerConcentric). New in 27, verified. iOS & iPadOS 27 release notes, verbatim: "You can now access concentricCornerRadii and concentricCornerRadii(in:) on GeometryProxy. These APIs return the corner radii that are concentric with the view's container shape as a RectangleCornerRadii?. You can use these values to drive custom drawing or layout that responds to the container's corners without rendering a ConcentricRectangle directly." Declarations: var concentricCornerRadii: RectangleCornerRadii? { get } and func concentricCornerRadii(in frame: CGRect) -> RectangleCornerRadii?. Both are 27.0 on iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS, and both return nil if no container shape is set. AppKit, macOS 27.0, from WWDC26 289 'Modernize your AppKit app': @NSCopying var cornerConfiguration: NSViewCornerConfiguration? { get } on NSView, overridden in a subclass. The radius type is NSViewCornerRadius (macOS and Mac Catalyst 27.0), with class var containerConcentric, class func containerConcentric(_: CGFloat) for a minimum, and fixed(_:). Session code: override var cornerConfiguration: NSViewCornerConfiguration? { let radius: NSViewCornerRadius = .containerConcentric(minimumCornerRadius); return .uniformCorners(radius: radius) }. So .containerConcentric exists only as an AppKit (NSViewCornerRadius) member, not a SwiftUI one.
- **Evidence:** https://developer.apple.com/documentation/swiftui/geometryproxy/concentriccornerradii
