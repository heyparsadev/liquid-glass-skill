- **Established truth:** SKILL.md frames the skill only around iOS 26. L8 is the title '# Liquid Glass — iOS 26 SwiftUI Skill'. L10 says 'introduced with iOS 26 / Xcode 26 (WWDC25)', which is historically accurate. The L3 and L21 triggers name iOS 26 / iPadOS 26 / macOS Tahoe. The WWDC26 Platforms State of the Union (session 102) says, verbatim: 'In this year's releases, you'll see updates to the foundations of how Liquid Glass is built, refinements to the new design that improve consistency, and new ways for iOS apps to adapt across devices and screen sizes.' / 'To maintain exceptional readability, we tuned Liquid Glass so it more effectively diffuses complex content behind it.' / 'And to establish more depth and separation, we also introduced a darkened edge along with brighter specular highlights.' / 'We also made it more personalizable with a new slider in settings to adjust Liquid Glass anywhere from ultra clear to fully tinted...' / 'Apps already using Liquid Glass get these improvements automatically when they run on this year's releases without even needing to recompile.' The September 2026 and June 2026 sections of the SwiftUI updates page do not mention glassEffect, Glass or GlassEffectContainer. Glass still has only clear, identity, regular, interactive(_:) and tint(_:). GlassEffectContainer still has only init(spacing:content:). Both types are marked 26.0 on every platform. The 2026 additions related to bars and chrome are: ToolbarContent.visibilityPriority(_:), ToolbarOverflowMenu, ToolbarItemPlacement.topBarPinnedTrailing and View.toolbarMinimizationBehavior(_:for:) (June 2026, Toolbars); TabRole.prominent (Tab bars); NavigationTransition.crossFade (Transitions); and, under September 2026 'Controls on the vertical axis', EnvironmentValues.toolbarVerticalEdge, View.toolbarVerticalBehavior(_:), axisBehavior(_:) with ToolbarItemAxisBehavior, and View.toolbarVerticalCompressionBehavior(_:).
- **Evidence:** https://developer.apple.com/videos/play/wwdc2026/102/

## Finding 37 — **CONFIRMED**

> "Don't insert custom glass between layers 1 and 2; let the system own that band." None of the audited files mention scroll edge effects.

- **Established truth:** 03-design-tokens.md L141 says, verbatim: 'Don't insert custom glass between layers 1 and 2; let the system own that band.' No file under skills/liquid-glass mentions scroll edge effects; grep finds them only in docs/research. The HIG Scroll views change log reads: 'June 8, 2026: Updated guidance for scroll edge effects.' Its 'Scroll edge effects' section says, verbatim: 'Prefer the automatic scroll edge effect style.' 'Where possible, use the default automatic style of the scroll edge effect.' 'If you use the soft scroll edge effect style instead, thoroughly test your interface to ensure your controls maintain legibility in a variety of contexts.' 'Only use a scroll edge effect when a scroll view is behind floating interface elements.' 'Scroll edge effects aren't decorative.' 'Apply one scroll edge effect per view.' WWDC26 session 278, 'Modernize your UIKit app', says: 'In particular, the .automatic style no longer switches between the existing soft and hard styles but provides its own visuals for additional clarity. If you have overridden the style from .automatic previously, that decision should be re-evaluated, especially when set to .soft, as that no longer matches the default system appearance.' The WWDC26 State of the Union says: 'When content scrolls under floating bars, a uniform toolbar appears across the top and keeps the text legible while improving contrast. This effect is applied automatically for standard toolbars and can be customized using the existing scroll edge effect APIs.' The matching SwiftUI APIs are scrollEdgeEffectStyle(_:for:) with ScrollEdgeEffectStyle (.automatic, .hard, .soft) and scrollEdgeEffectHidden(_:for:). They are marked 26.0 on all platforms and are not deprecated.
- **Evidence:** https://developer.apple.com/design/human-interface-guidelines/scroll-views
- **Notes:** Sources: apple-other (HIG JSON at tutorials/data/design/human-interface-guidelines/scroll-views.json), apple-video (WWDC26 sessions 278 and 102), and apple-doc (swiftui/scrolledgeeffectstyle.json). All quotes match. Caveats: (1) Session 278 is a UIKit session. The SwiftUI ScrollEdgeEffectStyle page has no note specific to version 27 and still says 'The system determines which style to apply based on the platform and context.' (2) In the State of the Union, the 'uniform toolbar' sentence sits in a passage about Mac and iPad, between macOS window corners and 'both on macOS and iPadOS'. It may therefore not describe iPhone. The HIG guidance does apply to iOS, iPadOS and macOS.

## Finding 40 — **CONFIRMED**

> "Color blind simulators (Xcode → Color Vision Tests)". Checklist L56: "Color Vision tests (Xcode)".

- **Established truth:** Apple documents no Xcode feature called 'Color Vision Tests' and no color-blindness simulator in Xcode. 05-accessibility.md L189 ('Color blind simulators (Xcode → Color Vision Tests)') and checklist L56 ('Color Vision tests (Xcode)') name a feature that does not exist. Apple documents these routes instead. (a) The Apple doc 'Performing accessibility testing for your app' says: 'To test with accessibility settings, turn on each of the following accessibility features in Settings > Accessibility, one at a time.' Its list includes 'Display & Text Size > Differentiate Without Color' and 'Display & Text Size > Color Filters > Red/Green Filter, Green/Red Filter, Blue/Yellow Filter'. (b) Accessibility Inspector, opened with Xcode > Open Developer Tool > Accessibility Inspector, has a Settings pane with a 'Differentiate without color' toggle and, on iOS, watchOS and tvOS, a 'Grayscale' toggle. It also has Window > Show Color Contrast Calculator for checking contrast. (c) The App Store Connect page 'Differentiate Without Color Alone evaluation criteria' says: 'A great way to evaluate your app is to try testing using the Grayscale color filter in Accessibility Display settings. While this's not a representation of what color-blind users see, it's a good way to discover unanticipated problems with the use of color in your app.' HIG Color, under 'Inclusive color', says: 'Avoid relying solely on color to differentiate between objects, indicate interactivity, or communicate essential information. When you use color to convey information, be sure to provide the same information in alternative ways so people with color blindness or other visual disabilities can understand it.'
- **Evidence:** https://developer.apple.com/documentation/accessibility/performing-accessibility-testing-for-your-app
- **Notes:** Sources: apple-doc (accessibility/accessibility-inspector.json, testing-system-accessibility-features-in-your-app.json, performing-accessibility-testing-for-your-app.json), apple-other (App Store Connect Help page; HIG color.json, read in full at both offsets; HIG accessibility.json). None of these pages mentions 'Color Vision' or a simulator. The correction is stronger than the finding said: the Color Filters path is documented by Apple, not only by secondary sources. Apple also says grayscale is not a simulation of color blindness, so the 'simulators' label is wrong as well. The finding's 'or Simulator' is not documented. Apple's list of features unavailable in Simulator (VoiceOver, Voice Control, Switch Control, Assistive Access) leaves out Color Filters, but no page says Color Filters works there. A WebSearch lead (secondary) was not relied on.

## Finding 41 — **CONFIRMED**

> "only tint glass for truly destructive primary actions". Destructive actions are styled .glassProminent at 05 L91-95 and 07 L335-341. 05 L98 says role .destructive gives "tint and shape cues across accessibility modes".

- **Established truth:** The Role section of HIG Buttons (page last updated December 16, 2025) says, verbatim: 'A button's role can have additional effects on its appearance. For example, a primary button uses an app's accent color, whereas a destructive button uses the system red color.' and 'Don't assign the primary role to a button that performs a destructive action, even if that action is the most likely choice. Because of its visual prominence, people sometimes choose a primary button without reading it first. Help people avoid losing content by assigning the primary role to nondestructive buttons.' Its Style section says: 'In general, use a button that has a prominent visual style for the most likely action in a view.' and 'Keep the number of prominent buttons to one or two per view.' The skill recommends 'truly destructive primary actions' (03 L66) and pairs role .destructive with .buttonStyle(.glassProminent) (05 L91-95, 07 L335-341). Both go against this guidance. The ButtonRole.destructive page (iOS 15.0+) says only that 'A destructive button signals by its appearance that the user should carefully consider whether to tap or click the button', with a red-background swipeActions example. It mentions no shape cues and nothing about accessibility modes. The GlassProminentButtonStyle page says nothing about roles or tint. So 05 L98's 'the system applies the right tint *and* shape cues across accessibility modes' is not documented.
- **Evidence:** https://developer.apple.com/design/human-interface-guidelines/buttons
- **Notes:** Sources: apple-other (HIG buttons.json, fetched twice for the full Role paragraph) and apple-doc (swiftui/buttonrole/destructive.json, swiftui/glassprominentbuttonstyle.json). All quoted HIG text matches. Caveat: the HIG wording is about the 'primary role' (accent color, Return key, default button), not literally the .glassProminent style. The conflict is inferred from the stated reason ('visual prominence') and from the Style section, which ties prominent styles to the most likely action. The inference is sound. No line in the HIG Role section links shape to a role.

## Finding 42 — **CONFIRMED**

> "Full-screen examples that compile in Xcode 26"

- **Established truth:** SKILL.md L37's claim ('Full-screen examples that compile in Xcode 26') cannot be checked without a Swift toolchain or CI. The documented API is 'nonisolated func glassEffect(_ glass: Glass = .regular, in shape: some Shape = DefaultGlassEffectShape()) -> some View', available on iOS, iPadOS, Mac Catalyst, macOS, tvOS and watchOS 26.0. It has no isEnabled parameter, and the doc path glasseffect(_:in:isenabled:) returns 404. glasseffecttransition(_:isenabled:) also returns 404; the documented form is 'func glassEffectTransition(_ transition: GlassEffectTransition) -> some View'. The reference files still use isEnabled: 01-api-reference L7, L19, L29, L51 and L224/L231 (the transition signature); 06-performance L162; 07-anti-patterns L127; plus prose in 02 L133/L166 and 06 L63. These do not match the documented API.
- **Evidence:** https://developer.apple.com/documentation/swiftui/view/glasseffect(_:in:)
- **Notes:** Sources: apple-doc (swiftui/view/glasseffect(_:in:).json; the 404s on the isEnabled variants; glasseffecttransition(_:).json). Caveat: the isEnabled problems are in references/, not examples/. The examples/*.swift files do not use isEnabled. I spot-checked these example APIs against the docs and all exist at 26.0: searchToolbarBehavior(.minimize) (the member is 'minimize', even though Apple's own sample writes '.minimized'), ToolbarSpacer(.fixed, placement:) via init(SpacerSizing, placement:), EnvironmentValues.tabViewBottomAccessoryPlacement, and GlassEffectContainer(spacing:). So the examples' compile claim is unverified, not shown to be false. The finding's call for CI evidence stands.
