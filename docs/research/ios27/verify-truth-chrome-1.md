_Phase: Verify — independent re-check of findings from [truth-chrome](truth-chrome.md)_

## Finding 0 — **CONFIRMED**

> `.sharedBackgroundVisibility(.hidden)` is applied to the Button inside `ToolbarItem { ... }`.

- **Established truth:** `sharedBackgroundVisibility(_:)` exists only on ToolbarContent: `nonisolated func sharedBackgroundVisibility(_ visibility: Visibility) -> some ToolbarContent`. It is available on iOS 26.0+, iPadOS 26.0+, Mac Catalyst 26.0+ and macOS 26.0+, is not deprecated in the current iOS 27 docs, and has no tvOS, visionOS or watchOS entries. Apply it to the ToolbarItem after its closing brace: `ToolbarItem { Button("Profile", systemImage: "person.crop.circle") { } }.sharedBackgroundVisibility(.hidden)`. Docs: "Hiding the effect will cause the item to be placed in its own grouping." There is no View overload, so putting the modifier on the Button inside the ToolbarItem closure (skill line 349) does not compile.
- **Evidence:** https://developer.apple.com/documentation/swiftui/toolbarcontent/sharedbackgroundvisibility(_:)
- **Notes:** apple-doc (DocC JSON): the declaration and platforms are as stated. Abstract: "Controls the visibility of the glass background effect on items in the toolbar. In certain contexts, such as the navigation bar on iOS and the window toolbar on macOS, toolbar items will be given a glass background effect that is shared with other items in the same logical grouping." The ToolbarContent page lists it under "Setting visibility". Evidence that no View overload exists: view/sharedbackgroundvisibility(_:).json returns HTTP 404; no 'sharedBackground' identifier appears on the View page (both chunks read) or the Toolbars collection page; Button's only listed conformance is View, so it cannot pick up the ToolbarContent method. apple-video WWDC25-323 (9:07, "Hide shared glass background"): `.toolbar { ToolbarItem { ProfileButton() }.sharedBackgroundVisibility(.hidden) }`, narrated as "Apply the sharedBackgroundVisibility modifier to separate an item into its own group without a background." This matches the skill's Profile example almost exactly. Caveat: Apple's DocC sample, which the finding quotes, writes `ToolbarItem(placement: principal)` without the leading dot. That typo is Apple's; real code needs `.principal`.

## Finding 1 — **CONFIRMED**

> Search is pinned to a toolbar placement by nesting `DefaultToolbarItem(kind: .search, placement: .bottomBar)` inside `ToolbarItem(placement: .bottomBar) { ... }`.

- **Established truth:** `DefaultToolbarItem` (`nonisolated struct DefaultToolbarItem`; "Conforms To" lists only ToolbarContent; iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS 26.0+) is toolbar content, not a View. `ToolbarItem` is declared `struct ToolbarItem<ID, Content> where Content : View`, and its `init(placement:content:)` is "Available when ID is () and Content conforms to View". Nesting DefaultToolbarItem inside `ToolbarItem(placement: .bottomBar) { }` therefore does not compile. Put it directly in the toolbar content: `.toolbar { ToolbarItem(placement: .bottomBar) { CalendarPicker() } ... DefaultToolbarItem(kind: .search, placement: .bottomBar); ToolbarSpacer(placement: .bottomBar); ... }` with `.searchable` applied. The initializer is `nonisolated init(kind: ToolbarDefaultItemKind, placement: ToolbarItemPlacement = .automatic)`, and its return value is "A `ToolbarItem` with content provided by the `kind`." If the system has already placed a matching item, this one "will implicitly replace the default-placed instance", so it moves or repositions the search item that `.searchable` adds.
- **Evidence:** https://developer.apple.com/documentation/swiftui/defaulttoolbaritem/init(kind:placement:)
- **Notes:** apple-doc: the declaration, return value, availability and the NavigationSplitView/CalendarPicker sample all match the finding verbatim. iOS 27 / Xcode 27 nuance I checked: ToolbarItem.init(placement:content:) is now declared with `@ContentBuilder content: () -> Content`. ContentBuilder is `typealias ContentBuilder = ViewBuilder`, and the docs say "In its build functions, ContentBuilder doesn't enforce protocol conformance." The init is still gated on `Content conforms to View`, and the struct still requires `Content : View`, so the nesting fails under Xcode 27 too. apple-video WWDC25-323 (8:47, "Toolbar items with flexible spacing") also puts `DefaultToolbarItem(kind: .search, placement: .bottomBar)` directly between `ToolbarSpacer(.flexible, placement: .bottomBar)` and `ToolbarSpacer(.fixed, placement: .bottomBar)`. `ToolbarDefaultItemKind.search` is documented as "The search item added by a searchable(text:isPresented:placement:prompt:) modifier." The docs also say some kind/placement combinations "may be valid on some platforms, but not on others". The finding's phrase "does not create a new one" is a fair gloss: the docs say it "Creates a system-defined toolbar item" that replaces the default-placed instance.

## Finding 2 — **CONFIRMED**

> Variation 'Search field in the bottom toolbar' wraps `DefaultToolbarItem(kind: .search, placement: .bottomBar)` inside `ToolbarItem(placement: .bottomBar) { }`.

- **Established truth:** patterns/glass-search-field.md lines 57-63 have the same compile error. DefaultToolbarItem conforms only to ToolbarContent, while both `ToolbarItem<ID, Content>` and `ToolbarItemGroup<Content>` require `Content : View`. Correct form: `.toolbar { DefaultToolbarItem(kind: .search, placement: .bottomBar) }` followed by `.searchable(text: $query)`. Strictly, it has to sit wherever ToolbarContent is expected: directly in `.toolbar { }`, inside ToolbarContent containers such as Group or ForEach, or in a custom ToolbarContent body. It can never go inside a ToolbarItem or ToolbarItemGroup view closure.
- **Evidence:** https://developer.apple.com/documentation/swiftui/defaulttoolbaritem
- **Notes:** apple-doc: the struct is `nonisolated struct DefaultToolbarItem`, its relationshipsSections contain only "Conforms To: ToolbarContent" (no View conformance, conditional or otherwise), and it is available on all seven platforms at 26.0. The overview says: "Place this item in your toolbar to control where the system-provided item, like search, will be positioned." The finding's "must be a direct child of .toolbar { }" is slightly overstated (see corrected claim). The sentence after the snippet also needs fixing: "This pins the search field above the tab bar — common in media apps where search is a destination rather than a global tool" is not supported by Apple. DefaultToolbarItem only positions the system search item within the toolbar. For a dedicated search destination, Apple recommends the search tab. HIG (apple-other): "Include search as an item in the sidebar or tab bar when you want an area dedicated to discovery ... like Music and TV", and "As an alternative to search in a tab bar, you can also place search in a toolbar either at the bottom or top of the screen."

## Finding 3 — **CONFIRMED**

> Inside the accessory, `@Environment(\.tabViewBottomAccessoryPlacement) var placement` takes the values `.expanded | .collapsed`.

- **Established truth:** `enum TabViewBottomAccessoryPlacement` (iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS 26.0+) has exactly two cases. `case expanded`: "The bar is expanded on top of the bottom tab bar, if there is a bottom tab bar, or at the bottom of the tab's content view." `case inline`: "The view is displayed in line with the bottom tab bar." There is no `.collapsed`, and the iOS 27 docs add no new case. The environment value is optional: `var tabViewBottomAccessoryPlacement: TabViewBottomAccessoryPlacement? { get }`, and "A nil value corresponds to an undefined placement." The comment should read `// .expanded | .inline (nil = undefined)`. Apple's WWDC25-323 sample: `if placement == .inline { // compact layout } else { // full layout }`.
- **Evidence:** https://developer.apple.com/documentation/swiftui/tabviewbottomaccessoryplacement
- **Notes:** apple-doc: the enum page, the EnvironmentValues/tabViewBottomAccessoryPlacement page and apple-video WWDC25-323 (5:39, "Tab bar accessory") all match the finding. The skill never writes `placement == .collapsed` in code; the error is the comment at 01-api-reference.md:396 plus the prose "expanded or collapsed" at patterns/glass-tab-bar.md:44. A reader following that comment would write code that does not compile. glass-tab-bar.md's `if placement == .expanded` compiles, but it treats nil as compact, the opposite of Apple's sample. Caveat: Apple's DocC overview sample uses `switch placement { case .inline: ... case .expanded: ... }` with no nil case and a missing closing brace. If the skill copies it, add `case nil:` or `default:` for the Optional. The HIG Tab bars page calls this an "attached accessory" with "expanded" and "minimized" art; it is not a source of any `.collapsed` case.

## Finding 5 — **PARTIALLY**

> "The `role: .search` tab is special: it surfaces the system search field at the top of the screen automatically."

- **Established truth:** Where the search field appears depends on platform and style, so neither "at the top of the screen" nor the finding's single location is right everywhere. Prerequisite (WWDC25-323): "set a search role on one of your tabs and place a searchable modifier on your TabView." iPhone: "When someone selects this tab, a search field takes the place of the tab bar, and the content of the tab is shown." iPad and Mac: "when someone selects the search tab, the search field appears centered above your apps browsing suggestions." Adopting Liquid Glass: "The system automatically separates the search tab from other tabs and places it at the trailing end." In iOS 27, the `TabRole.prominent` docs (27.0+) say "When there are no tabs with an explicit .prominent role, then a .search role tab may receive the prominent visual treatment by default." The HIG (updated June 8, 2026) gives two iOS search-tab styles. Standard tab: "navigates people to a search landing page with a search field at the top." Button appearance: "Tapping the search tab brings focus to the search field and displays the keyboard." The HIG names no SwiftUI API for choosing between them. `tabViewSearchActivation(.searchTabSelection)` (iOS, iPadOS, Mac Catalyst and macOS 26.0+) "Links the search tab's selection to search activation"; by default "search is only activated and deactivated by the user."
- **Evidence:** https://developer.apple.com/videos/play/wwdc2025/323/
- **Notes:** Every quote in the finding is verbatim-accurate. Sources checked: the apple-doc updates page (June 2025 bullet), apple-video WWDC25-323, the Adopting Liquid Glass page, apple-doc TabRole.search ("Searchable tab views will prefer to have the first tab with this role implement search. If no tabs are specified as the search tab, the tab view will apply search to all tabs..."), and the apple-other HIG search-fields page. TabRole.search availability is right: iOS 18.0, iPadOS 18.0, Mac Catalyst 18.0, macOS 15.0, tvOS 18.0, visionOS 2.0, watchOS 11.0. However, "factually-wrong" overstates it. The skill's "top of the screen" is wrong for the default iPhone behavior, where the field replaces the tab bar at the bottom. It roughly matches iPad and Mac (the finding left out that sentence, which is in the same WWDC session) and the iOS 27 HIG Standard-tab style. The fix should make the sentence platform- and style-specific. The skill's own search-tab examples do apply `.searchable` to the TabView. Secondary lead only, not fact: Apple Developer Forums thread 834952 (a user report on an iOS 27 beta) describes a search tab putting the field at the top, attached to the nav bar. The DTS reply only asked for a sample, so it is inconclusive.

## Finding 6 — **PARTIALLY**

> "When the search tab is active, the search field automatically takes prominence in the nav layer."

- **Established truth:** The skill's sentence is vague rather than false. Apple says Liquid Glass "applies to the topmost layer of the interface, where you define your navigation. Key navigation elements like tab bars and sidebars float in this Liquid Glass layer" (Adopting Liquid Glass). On iPhone, the field that "takes the place of the tab bar" is therefore in the navigation layer. On iPad and Mac it "appears centered above your apps browsing suggestions" (WWDC25-323). Precise wording: "Selecting the search tab replaces the tab bar with the search field on iPhone; on iPad and Mac the field appears centered above the tab's browsing suggestions." Separately, iOS 27 adds `TabRole.prominent` (`static var prominent: TabRole { get }`, 27.0+ on every platform): "A tab role that provides prominent visual treatment to one of the tabs in supported tab bars. Only one tab can receive the prominent treatment. When there are no tabs with an explicit .prominent role, then a .search role tab may receive the prominent visual treatment by default." That treatment applies to the tab item (June 2026 updates: "place the tab in a separate, trailing position of the tab bar"), not to the search field.
- **Evidence:** https://developer.apple.com/documentation/swiftui/tabrole/prominent
- **Notes:** Verified: the TabRole.prominent quote and availability (iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS 27.0, not beta) from apple-doc, and TabRole.search `static var search: TabRole { get }` at iOS 18.0+. Also verified that the field takes the place of the tab bar on iPhone (WWDC25-323). The finding's key contrast, that the field is "not 'in the nav layer'", contradicts Apple's Liquid Glass terminology. It also contradicts the skill's own definition (SKILL.md:84 "Glass is the navigation layer ... nav bars, tab bars, toolbars"; references/02-hig-principles.md:12). So the claim that the skill is factually wrong is refuted; the skill is only imprecise. Rewording is still worthwhile: "takes prominence" now collides with the iOS 27 `.prominent` tab role, which governs where the tab sits, not where the field appears. The finding's evidence_url points at prominent (27.0+), but its availability field gives search's 18.0+; both values are correct for their own symbols.
