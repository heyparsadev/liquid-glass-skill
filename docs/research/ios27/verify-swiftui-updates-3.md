# verify:swiftui-updates#3

_Phase: Verify — independent re-check of findings from [swiftui-updates](swiftui-updates.md)_

## Finding 12 — **CONFIRMED**

> Button styles section offers only `.buttonStyle(.glass)` and `.buttonStyle(.glassProminent)`; a configurable glass button requires .glassEffect on a Button.

- **Established truth:** The skill's Button styles section (01-api-reference.md:252-259) offers only .glass and .glassProminent and says not to 'roll your own with .glassEffect() on a Button', so it omits the configurable style. Apple documents PrimitiveButtonStyle.glass(_:): `nonisolated static func glass(_ glass: Glass) -> Self`, available when Self is GlassButtonStyle. Abstract: 'A button style that applies a configurable Liquid Glass effect based on the button's context.' Example: `Button("Button") {}.buttonStyle(.glass(.clear))`. Availability: iOS, iPadOS, Mac Catalyst, macOS, tvOS and watchOS 26.0, with no visionOS. GlassButtonStyle also has `nonisolated init(_ glass: Glass)`, introduced 26.1 on the same six platforms; its page has no abstract or discussion. The tvOS sentence ('In tvOS, this button style applies a Liquid Glass effect regardless of whether the button has focus. This style is similar to the bordered style.') is on the glass(_:) page, not the init page.
- **Evidence:** https://developer.apple.com/documentation/swiftui/primitivebuttonstyle/glass(_:)
- **Notes:** Source: apple-doc. Checked against the DocC JSON, including the raw metadata.platforms arrays and declaration tokens for glass(_:) (26.0) and GlassButtonStyle/init(_:) (26.1). Apple's docs disagree with themselves here: the static factory says 26.0 but the GlassButtonStyle init it wraps says 26.1. The finding reports both values accurately. Apple's PrimitiveButtonStyle page lists glass, glass(_:) and glassProminent under 'Getting built-in button styles'. The GlassButtonStyle overview says 'You can also use glass to construct this style.' The finding's only flaw is minor: it places the tvOS quote right after the init(_:) sentence, but the quote actually comes from glass(_:).

## Finding 14 — **CONFIRMED**

> `.glassEffect(_:in:isEnabled:)` with `isEnabled: Bool = true`; also used at references/07-anti-patterns.md:127, references/06-performance.md:162 and references/02-hig-principles.md:133.

- **Established truth:** Apple documents a single declaration: `nonisolated func glassEffect(_ glass: Glass = .regular, in shape: some Shape = DefaultGlassEffectShape()) -> some View`. Availability: iOS, iPadOS, Mac Catalyst, macOS, tvOS and watchOS 26.0. It has no isEnabled parameter. /documentation/swiftui/view/glasseffect(_:in:isenabled:) returns HTTP 404. The glassEffect page, its 'Styling views with Liquid Glass' See Also list, and the 'Applying Liquid Glass to custom views' article never mention isEnabled. DefaultGlassEffectShape is documented as 'The default shape applied by glass effects, a capsule.' The skill's isEnabled usages match no documented signature: 01-api-reference.md:7, 19, 29 and 51; 07-anti-patterns.md:127; 06-performance.md:162; and the prose at 02-hig-principles.md:133 and 166 and 06-performance.md:63. The documented way to opt out is Glass.identity: 'When applied, your content remains unaffected as if no glass effect was applied.'
- **Evidence:** https://developer.apple.com/documentation/swiftui/view/glasseffect(_:in:)
- **Notes:** Source: apple-doc. The raw tokens confirm exactly one entry in the declarations array, with defaults '= .regular' and '= DefaultGlassEffectShape()'. The skill's separately listed `func glassEffect() -> some View` overload is also undocumented; the no-argument call works through the default values. The skill also writes the shape default as `S = DefaultGlassEffectShape` with no parentheses. Caveat: view.json does not enumerate View modifiers, so 'only overload' rests on the 404, the See Also list and the article. That is strong evidence but not an exhaustive index scan.

## Finding 15 — **CONFIRMED**

> `func glassEffectTransition(_ transition: GlassEffectTransition, isEnabled: Bool = true)` and `enum GlassEffectTransition { case identity; case matchedGeometry; case materialize }`

- **Established truth:** The modifier is `@MainActor @preconcurrency func glassEffectTransition(_ transition: GlassEffectTransition) -> some View`, with no isEnabled parameter. GlassEffectTransition is `struct GlassEffectTransition` (conforms to Sendable and SendableMetatype), not an enum. Its type properties are `static var identity: GlassEffectTransition`, `static var matchedGeometry: GlassEffectTransition` and `static var materialize: GlassEffectTransition`. The other declarations are `nonisolated func glassEffectID(_ id: (some Hashable & Sendable)?, in namespace: Namespace.ID) -> some View` and `@MainActor @preconcurrency func glassEffectUnion(id: (some Hashable & Sendable)?, namespace: Namespace.ID) -> some View`. GlassEffectContainer is declared `@MainActor @preconcurrency struct GlassEffectContainer<Content> where Content : View` and lists one initializer: `@MainActor @preconcurrency init(spacing: CGFloat? = nil, @ContentBuilder content: () -> Content)`. All are iOS, iPadOS, Mac Catalyst, macOS, tvOS and watchOS 26.0.
- **Evidence:** https://developer.apple.com/documentation/swiftui/glasseffecttransition
- **Notes:** Source: apple-doc. Each declaration was checked on its own DocC JSON page. Nuance: ContentBuilder is documented as `typealias ContentBuilder = ViewBuilder` (iOS 13.0+, and announced on the SwiftUI updates page under June 2026 / Xcode 27). So the skill's `@ViewBuilder` spelling is equivalent and not an error in itself. The real container discrepancy is the extra `init(@ViewBuilder content:)` overload the skill lists; `GlassEffectContainer { }` still works because spacing defaults to nil. Call sites like `.glassEffectTransition(.materialize)` and string IDs compile unchanged. The signature difference matters for non-Sendable IDs and for passing nil. Apple's 'Applying Liquid Glass to custom views' article says: 'For effects you want to add or remove that are positioned within the container's assigned spacing, the default transition type is matchedGeometry.'

## Finding 16 — **CONFIRMED**

> Minimum requirements table lists visionOS 26.0+ for Liquid Glass; SKILL.md frontmatter also lists visionOS 26+.

- **Established truth:** None of the Liquid Glass material symbols list visionOS. Each lists only iOS, iPadOS, Mac Catalyst, macOS, tvOS and watchOS. Symbols checked: Glass, glassEffect(_:in:), DefaultGlassEffectShape, GlassEffectContainer and its init(spacing:content:), glassEffectID(_:in:), glassEffectUnion(id:namespace:), glassEffectTransition(_:), GlassEffectTransition, GlassButtonStyle (including init(_:) at 26.1), GlassProminentButtonStyle and PrimitiveButtonStyle.glass(_:). So the skill is wrong to list visionOS 26.0+ for these: 01-api-reference.md:532, plus SKILL.md:3 (description) and SKILL.md:5 (platforms). The visionOS glass API is `nonisolated func glassBackgroundEffect<T, S>(_ effect: S, in shape: T, displayMode: GlassBackgroundDisplayMode = .always) -> some View where T : InsettableShape, S : GlassBackgroundEffect`, at visionOS 2.4. Exact versions: the GlassBackgroundEffect protocol is visionOS 2.4 (members .automatic, .plate, .feathered and feathered(padding:softEdgeRadius:)). The GlassBackgroundDisplayMode enum is visionOS 1.0 (.always, .implicit, .never). glassBackgroundEffect(displayMode:) appears on the SwiftUI updates page under 'June 2023, visionOS'.
- **Evidence:** https://developer.apple.com/documentation/swiftui/view/glasseffect(_:in:)
- **Notes:** Source: apple-doc. The finding's parenthetical 'GlassBackgroundEffect / GlassBackgroundDisplayMode (visionOS 1.0/2.4)' pairs the versions in reverse order. The correct pairing is GlassBackgroundEffect = 2.4 and GlassBackgroundDisplayMode = 1.0. Scope the fix: some companion APIs the skill covers do list visionOS. ConcentricRectangle, Edge.Corner.Style, Shape.rect(corners:isUniform:) and GeometryProxy.containerCornerInsets are visionOS 26.0, and GeometryProxy.concentricCornerRadii is visionOS 27.0. Remove visionOS for the glassEffect family and button styles, and do not claim that nothing in the skill applies there.

## Finding 17 — **CONFIRMED**

> `.rect(cornerRadius: .containerConcentric)` matches the parent radius; also used in SKILL.md golden rule 4, 03-design-tokens.md, 02-hig-principles.md, 07-anti-patterns.md, glass-card-stack.md and the pre-ship checklist.

- **Established truth:** `containerConcentric` is not a SwiftUI symbol. It appears nowhere on the ConcentricRectangle, Edge.Corner.Style or Shape pages. Also, `Shape.rect(cornerRadius:style:)` is `static func rect(cornerRadius: CGFloat, style: RoundedCornerStyle = .continuous) -> Self`, which takes a CGFloat only, so `.rect(cornerRadius: .containerConcentric)` cannot type-check. The shipping API is available on all seven platforms (including visionOS) at 26.0: (1) `struct ConcentricRectangle`, with init(), init(corners:isUniform:), individual-corner initializers (topLeadingCorner:...) and uniform initializers (uniformTopCorners:, uniformBottomCorners:, uniformLeadingCorners:, uniformTrailingCorners: and their combinations), each with a matching static Shape.rect(...) factory. (2) `Edge.Corner.Style`, a struct that is ExpressibleByFloatLiteral and ExpressibleByIntegerLiteral, with `static var concentric`, `static func concentric(minimum: Edge.Corner.Style? = nil) -> Edge.Corner.Style` and `static func fixed(_: CGFloat) -> Edge.Corner.Style`. (3) `static func rect(corners: Edge.Corner.Style, isUniform: Bool = false) -> Self`. Concentric radii resolve against system containers such as sheets and popovers, or against a `containerShape(_:)` that implements RoundedRectangularShape. Replace the skill's usage with `.rect(corners: .concentric)`, `.rect(corners: .concentric(minimum: 12))` or `ConcentricRectangle()`.
- **Evidence:** https://developer.apple.com/documentation/swiftui/concentricrectangle
- **Notes:** Sources: apple-doc and apple-video. Likely origin of the error: WWDC25 session 323, 'Build a SwiftUI app with the new design', at 17:27 showed a pre-release spelling, `.background(.tint, in: .rect(corner: .containerConcentric))`. That spelling did not ship (Apple developer forum threads, used here only as a secondary lead, say corners/.concentric arrived in Xcode 26 beta 4). The skill's `cornerRadius:` label matches neither the WWDC spelling nor the shipping API. Minor: the finding's concentric(minimum:) declaration omits the `= nil` default shown on its detail page. Fix caveat: the 'Right' example at 07-anti-patterns.md:149-156 only draws the parent radius with `.background(RoundedRectangle(cornerRadius: 28)...)`. Per the ConcentricRectangle docs, a custom parent must also declare `.containerShape(RoundedRectangle(cornerRadius: 28))`, so renaming to `.concentric` alone will not produce concentric corners. All skill locations were confirmed by grep: 01-api-reference.md:466, 473 and 475; SKILL.md:87; 03-design-tokens.md:13, 18 and 152; 02-hig-principles.md:20, 27, 82 and 154; 07-anti-patterns.md:154; patterns/glass-card-stack.md:92; checklists/pre-ship-checklist.md:26.

## Finding 18 — **CONFIRMED**

> Concentric corners section offers only shape-based concentricity.

- **Established truth:** iOS 27 adds two GeometryProxy members: `var concentricCornerRadii: RectangleCornerRadii? { get }` and `func concentricCornerRadii(in frame: CGRect) -> RectangleCornerRadii?`. Both are introduced at 27.0 on iOS, iPadOS, Mac Catalyst, macOS, tvOS, visionOS and watchOS. Return value, verbatim: 'The resolved corner radii, or nil if no container shape is set or the shape does not provide sufficient corner info.' Discussion, verbatim: 'Unlike ConcentricRectangle, which calculates and draws the shape, this property only returns the calculated radii.' (The (in:) variant says 'this function'.) The iOS & iPadOS 27 Release Notes, under SwiftUI New Features, say: 'You can now access concentricCornerRadii and concentricCornerRadii(in:) on GeometryProxy. These APIs return the corner radii that are concentric with the view's container shape as a RectangleCornerRadii?. You can use these values to drive custom drawing or layout that responds to the container's corners without rendering a ConcentricRectangle directly. (177185166)'. The skill's concentric section (01-api-reference.md:472-476) covers only shapes, and the shape it names (.containerConcentric) does not exist.
- **Evidence:** https://developer.apple.com/documentation/swiftui/geometryproxy/concentriccornerradii
- **Notes:** Sources: apple-doc and apple-other. Release note 177185166 was confirmed in https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes (second half of the page); a web search does not index that number. Apple's examples pair the API with `.containerShape(.rect(cornerRadius: 48))` inside a GeometryReader and Canvas. Because the skill targets iOS 26+, any use needs an `if #available(iOS 27, *)` gate. Related, but outside the finding: GeometryProxy.containerCornerInsets (RectangleCornerInsets, 26.0, including visionOS) is another corner-geometry API the skill does not mention.
